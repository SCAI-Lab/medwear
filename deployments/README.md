# Installation-specific configuration

This repository holds the MEDWEAR platform: the API, web interface, nginx,
database migrations, the Keycloak realm template and the stack in
`docker-compose.yml`. Nothing in it belongs to a particular installation.

What is specific to one installation stays out of this repository:

- `.env` and `.env.medwear`, generated by `setup.sh`
- a `docker-compose.override.yml` with only what differs from
  `docker-compose.yml`: extra services, certificates, host paths, published
  ports, resource limits
- a realm export, if accounts are kept across a reset
  (`scripts/export_realm.sh <file>`)
- project-specific import scripts and pipelines

If you manage several installations, keep each one's override and scripts in
a folder of a private repository of your own, next to this checkout.

## Settings without an override

These variables of `docker-compose.yml` can be set in `.env`:

| Variable | Default | Meaning |
|---|---|---|
| `MEDWEAR_ENV_FILE` | `.env.medwear` | environment file of the services |
| `MEDWEAR_HTTP_PORT` | `80` | published HTTP port of nginx, optionally with a bind address (`127.0.0.1:8080`) |
| `MEDWEAR_HTTPS_PORT` | `443` | published HTTPS port of nginx |
| `MEDWEAR_KEYCLOAK_PORT` | `8180` | published port of the Keycloak console |

## Using an override

Docker Compose reads `docker-compose.override.yml` next to
`docker-compose.yml` on every command; git ignores that file here. Keep the
real file in your own repository and link it:

```bash
ln -s ../<your-config>/<installation>/docker-compose.override.yml docker-compose.override.yml
docker compose config    # the merged configuration, to check what will run
docker compose up -d
```

Relative paths in the override are resolved from this directory.

Example: your own certificate, and the databases published on the loopback
interface only:

```yaml
services:
  medwear-nginx:
    volumes:
      - /etc/ssl/medwear/server.crt:/etc/nginx/certs/localhost.crt:ro
      - /etc/ssl/medwear/server.key:/etc/nginx/certs/localhost.key:ro
  postgres:
    ports: !override
      - "127.0.0.1:5433:5432"
  influxdb:
    ports: !override
      - "127.0.0.1:8086:8086"
```

An override can add services and change settings, but it cannot remove what
`docker-compose.yml` declares. To leave a service out, give it a profile that
is never enabled (`profiles: [disabled]`). Lists such as `ports` are
extended; `!override` replaces them and `!reset []` empties them (Docker
Compose 2.24 or later). podman-compose 1.6 does not substitute variables
inside `!override` and accepts it only on keys that `docker-compose.yml`
already has.

The [MEDWEAR benchmark](https://github.com/SCAI-Lab/medwear-benchmark)
(`bench/compose/medwear-bench.override.yml`) is a complete example: an
isolated stack per job with its own names, ports and settings.
